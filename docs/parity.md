# Parity with manuzio

kuleshov must produce what manuzio's own crates (`mnz-audios`, `mnz-videos`)
produced. The references in
[crates/parity/references/](../crates/parity/references) were recorded from
those crates at the commit in [manuzio-source.md](manuzio-source.md), and the
parity test ([crates/parity/tests/parity.rs](../crates/parity/tests/parity.rs))
checks kuleshov against them. manuzio can run the same check after switching
(see the end).

## What is recorded

58 scenarios call every public function over fixed inputs: durations, MP3
encodes (variable and constant bit rate, room tone, tags, a folder with Chinese
characters and apostrophes), slots and WAV joins, analyses, the four camera
movements at 90×160 and one faded full-HD clip, joins by stream copy and by
filter, muxes, the async variants, and the errors and cancellations (a flag
already set, so that nothing starts). The inputs are generated by
[fixtures.rs](../crates/parity/src/fixtures.rs): WAV tones and PPM stills, so
they never depend on an FFmpeg build. Later scenarios read earlier outputs.

For each scenario the reference holds:

- **the calls:** every `ffmpeg` and `ffprobe` run, with its arguments in order
  and the contents of the concat lists among them. A recording shim
  ([kuleshov-record](../crates/parity/src/bin/kuleshov-record.rs)), copied as
  `ffmpeg` and `ffprobe` into a folder that the code under test takes for its
  tools folder (`MNZ_TOOLS_DIR` on manuzio's side, `Tools::find_in` here), logs
  them and runs the real program with the same arguments and standard streams;
- **the result:** the value returned, written with `{:?}`, or the error
  message;
- **the outputs:** each returned file's size and SHA-256, the MD5 of its
  decoded audio (`-f md5`), the SHA-256 of its decoded video's `-f framemd5`
  listing with the number of frames, and ffprobe's stream and format
  parameters;
- **the files left** in the scenario's folder: no concat list, no partial
  output.

Machine-specific text is named, in the arguments, lists, results and file
names alike ([session.rs](../crates/parity/src/session.rs)): a returned file as
`{scenario#n}`, the work folder as `{work}`, a generated UUID as `{uuid1}`,
`{uuid2}`… in order of appearance, and the memory addresses in FFmpeg's log
prefixes as `{address}`. Path separators are kept, so each platform has its
own file.

## How they are compared

[compare.rs](../crates/parity/src/compare.rs):

- the FFmpeg and FFprobe builds must be those of the references;
- the calls, concat lists and files left must be equal;
- a result must be equal, or both must be errors (kuleshov's typed errors
  word their messages differently from manuzio's `anyhow` chains, and name the
  file in more of them);
- every output must be equal **byte for byte**.

The one exception is **room tone**. FFmpeg's `anoisesrc` is seeded at random
unless it is given a seed, and manuzio gives none, so two encodes with room
tone differ in their noise even from manuzio itself (two recordings on the same
machine differed). For the scenarios that ask for room tone, and those that
read their outputs, the arguments must still be equal, the outputs' stream
parameters must be equal except for the bit rate and duration (which follow
the noise in a variable-bit-rate encode), and measured values must agree
within 1.5 (the noise floor of the same encode moved by about 0.6 dB between
recordings). Every other output, MP3s, WAVs and x264 MP4s alike, was the same
byte for byte across recordings, so no other output needs the decoded hashes;
they are kept to tell a reader whether differing bytes still decode to the
same audio and video.

## The reference builds

The references belong to one FFmpeg build per platform, pinned in
[crates/kuleshov/ffmpeg-builds.json](../crates/kuleshov/ffmpeg-builds.json)
(read by `scripts/downloads.ts` and the `download` feature) and staged by
`mise run tools`:

| Platform | Build | `ffmpeg` SHA-256 | `ffprobe` SHA-256 |
| --- | --- | --- | --- |
| Windows x64 | gyan.dev 9.0.2 essentials (`ffmpeg version 9.0.2-essentials_build-www.gyan.dev`) | `3256173f3f8bffd7df12227c68adf68025edb1832273a9530688a7bb1ed8edec` | `f0d36ecbbdd3bcfac3efa078c96c7271c2e68b3810595552ac3b7f17e9a65c52` |
| Linux x64 | johnvansickle 7.0.2 amd64 static (`ffmpeg version 7.0.2-static`) | `e7e7fb30477f717e6f55f9180a70386c62677ef8a4d4d1a5d948f4098aa3eb99` | `4f231a1960d83e403d08f7971e271707bec278a9ae18e21b8b5b03186668450d` |

The two platforms' argument lists are the same apart from path separators;
their outputs differ, as their encoders do. A pin that changes means new
references, recorded from manuzio again: ask the owner first.

## Recording them again

Only from manuzio's crates, never from kuleshov itself, and never edited by
hand. The harness is kept in the gitignored `tmp/` (owner's decision): to
rebuild it, make a crate outside the workspace (its own `[workspace]` table)
with path dependencies on `../manuzio/crates/audios`, `../manuzio/crates/videos`
and `crates/parity`, whose `main` takes the shim, the real tools folder, a work
folder and the output file, sets `MNZ_TOOLS_DIR` to the session's shim folder
before anything else, and runs the body of `run` in the parity test with
manuzio's functions (the same calls without the `&Tools` argument). The
scenarios must stay the same on both sides, one for one.

- **Windows:** `cargo build -p kuleshov_parity --bin kuleshov-record`, build
  the harness, and run it with `target/debug/kuleshov-record.exe`,
  `../manuzio/assets/tools`, a work folder and the output file.
- **Linux (WSL):** build and run both natively in WSL (with a C toolchain,
  such as Ubuntu's `build-essential`) with the pinned 7.0.2 build, which
  `cargo run -p kuleshov --features download --example install_ffmpeg -- <folder>`
  installs. Without a C toolchain, both programs can instead be
  cross-compiled on Windows for `x86_64-unknown-linux-musl`, linked by the
  bundled rust-lld (`CARGO_TARGET_X86_64_UNKNOWN_LINUX_MUSL_LINKER=rust-lld`),
  as the references were first recorded.

Record twice on each platform and compare: only the room-tone outputs may
differ.

## The check in manuzio

After switching, manuzio checks the commit it pins with its own staged
FFmpeg (`assets/tools`, the Windows reference build on its development
machine), from a checkout of kuleshov at that commit:

```sh
KULESHOV_TOOLS_DIR=../manuzio/assets/tools cargo test -p kuleshov_parity
```

It must pass, with no change to the references.
